The FastAPI Backend

Ground-to-high-level: what FastAPI is, how PredictiX's API is structured, the request lifecycle, every folder and key file, how auth and the database work, how to run it, and its limits.

1 · What is FastAPI (ground level)?

FastAPI is a modern Python web framework for building HTTP APIs. You write plain Python functions, annotate them with type hints, and FastAPI handles routing, request parsing, validation, and documentation automatically.

  • ASGI & async — runs on an ASGI server (uvicorn); endpoints can be async for concurrency.
  • Type hints → behaviour — a parameter typed page: int is auto-parsed and validated; a Pydantic model body is auto-validated.
  • Pydantic — data-validation library; defines request/response shapes ("schemas").
  • Dependency injection — Depends(...) wires shared logic (DB session, current user) into endpoints.
  • Auto docs — interactive Swagger UI at /docs and the OpenAPI spec at /openapi.json, generated from your code.
Mental model: a router maps a URL to a Python function; FastAPI fills that function's arguments (from the request + dependencies), runs it, and serialises the return value to JSON.

2 · How it's used in this project

The backend is the single API layer between the Next.js frontend and everything else — the Supabase database, the ML models, the LLM, and the knowledge base. It exposes 34 routers covering auth, users/profiles, assets, tickets, predictions, the warehouse dashboard/report, notifications, a chatbot, FAQs, and diagnostics.

3 · Architecture & layers

The code is organised in clean layers — each has one job:

HTTP request │ ▼ routers/ ← URL → function; parse & validate I/O (thin) │ Depends(get_db), Depends(get_current_user) ▼ services/ + agents/ + ai/ ← business logic, ML, LLM, RAG │ ▼ models.py (SQLAlchemy ORM) ← table definitions │ ▼ db/session.py → Supabase Postgres ← the database ▲ schemas/ (Pydantic) ← request/response shapes used by routers core/ (config, security/JWT) ← cross-cutting settings & auth deps.py (get_db, get_current_user)← shared dependencies
Why layers? Routers stay thin (easy to read), business logic is reusable and testable in services/, and the data shape (schemas) is decoupled from the DB tables (models).

4 · Request lifecycle (a concrete trace)

Example: GET /user/tickets/stats (the user-ticket KPI counts):

  1. Routing — FastAPI matches the path to my_ticket_stats() in routers/user_tickets.py.
  2. Dependencies resolve — Depends(get_current_user) decodes the JWT bearer; Depends(get_db) opens a SQLAlchemy session.
  3. Validation — query/path params are coerced & checked against their type hints (else auto-422).
  4. Business logic — the endpoint calls svc.get_user_ticket_status_counts(db, current_user.id) in services/user_ticket_service.py.
  5. Data access — SQLAlchemy issues a GROUP BY status query to Supabase.
  6. Serialization — the return value is converted to JSON (validated against a Pydantic response_model when declared).
  7. Cleanup — get_db's finally closes the session; the JSON response is sent.

5 · App bootstrap (app/main.py)

main.py builds the application and wires everything together:

  • Lifespan — an @asynccontextmanager runs on startup: it loads the local predictive-maintenance models (classifier + regressor .pkl) and optionally warms the HuggingFace models (ticket categoriser, asset summariser), unless DISABLE_HF_MODELS=true.
  • CORS — allows the frontend origins (localhost:3000/3001, Vite 5173) to call the API.
  • Router registration — ~34 app.include_router(...) calls grouped by domain (auth, assets, tickets, predictions, reports, chatbot, diagnostics).
  • Health — a root / endpoint for liveness.
@asynccontextmanager
async def lifespan(_: FastAPI):
    clf_model = _load_pickle(CLF_MODEL_PATH)      # PdM classifier
    reg_model = _load_pickle(REG_MODEL_PATH)      # days-to-maintenance regressor
    if os.getenv("DISABLE_HF_MODELS") != "true":
        warmup_ticket_categorizer(); warmup_asset_summary_model()
    yield                                          # ← app serves requests here
app = FastAPI(title="PredictiX API", version="1.0", lifespan=lifespan)

6 · Auth & dependencies (app/deps.py)

Two dependencies power most endpoints:

get_db()

Yields a SQLAlchemy session and always closes it in finally (session-per-request). If no DB is configured it yields None so dev environments don't hang.

get_current_user()

Uses OAuth2PasswordBearer(tokenUrl="/auth/login") to read the Authorization: Bearer … header, decodes the JWT with python-jose (JWT_SECRET, HS256), looks up the Profile, and returns it (with a dev-friendly mock-profile fallback). Invalid/missing token → 401.

def get_current_user(token=Depends(oauth2_scheme), db=Depends(get_db)):
    payload = jwt.decode(token, JWT_SECRET, algorithms=["HS256"])
    user_id = payload["sub"]
    return db.query(Profile).filter(Profile.id == user_id).first()  # → endpoint
Any endpoint that declares current_user: Profile = Depends(get_current_user) is automatically protected — no token, no access. This is how /user/tickets scopes data to the caller.

7 · Data & validation layers

Database — SQLAlchemy + Supabase

db/session.py creates the engine from DATABASE_URL (or builds it from PROJECT_REF + DATABASE_PASSWORD for the Supabase pooler), with pool_pre_ping for resilient connections. models.py defines the ORM tables (Asset, AssetFailurePrediction, AssetCostPrediction, MaintenanceEvent, Ticket, Profile, Warehouse, …).

Validation — Pydantic schemas

schemas/ holds request and response models. A router declares response_model=TicketOut and FastAPI guarantees the output matches that shape (and documents it). Bad input is rejected with an automatic 422 and a precise error.

9 · How it was implemented (patterns)

  • APIRouter per domain — each file does router = APIRouter(prefix="/tickets", tags=["Tickets"]) and main.py includes them; clean URL grouping & docs.
  • Thin routers, fat services — endpoints validate & delegate; logic lives in services//agents/.
  • Dependency injection — DB session & current user via Depends, so they're consistent and testable.
  • Schema-first I/O — Pydantic models define and enforce every request/response.
  • Session-per-request — one DB session opened/closed per call (no leaks).
  • Startup warmup — heavy models load once at boot, not per request.
  • Graceful degradation — missing DB/HF config yields safe fallbacks instead of crashes (dev-friendly).
  • Numbers in Python, prose in LLM — the report layer computes figures deterministically (see the LLM guide).

10 · How to use it

Setup

cd PredictiX_backend/PredictiX_backend
python -m venv .venv && .venv\Scripts\activate    # Windows
pip install -r requirements.txt

Create .env:

DATABASE_URL=postgresql+psycopg2://...        # or PROJECT_REF + DATABASE_PASSWORD
JWT_SECRET=change-me                          # JWT signing
JWT_ALGORITHM=HS256
GROQ_API_KEY=gsk_xxx                          # LLM (report/chatbot)
HF_TOKEN=hf_xxx                               # HF models
# DISABLE_HF_MODELS=true                       # skip HF warmup in dev

Run

uvicorn app.main:app --reload                 # dev server on :8000

Explore & call

  • Open http://127.0.0.1:8000/docs — try any endpoint interactively.
  • From code/cURL:
curl -X POST http://127.0.0.1:8000/auth/login \
     -H "Content-Type: application/json" \
     -d '{"email":"...","password":"...","role":"admin"}'
# then send the returned token:
curl http://127.0.0.1:8000/user/tickets/stats \
     -H "Authorization: Bearer <token>"
Restart rule: after editing backend code (or pulling/merging), do a full Uvicorn restart — --reload can miss git-delivered changes, leaving stale code serving stale results.

12 · Limitations

  • Heavy startup. Loading PdM pickles + warming HF models slows boot and uses memory; HF warmup can fail the whole startup unless DISABLE_HF_MODELS=true.
  • Sync DB driver. SQLAlchemy + psycopg is synchronous, so async endpoints can still block on DB I/O under load; no async pool/ORM yet.
  • Dev-oriented auth. JWT_SECRET defaults to a placeholder and there's a mock-profile fallback — fine for dev, must be hardened (real secret, no mock) for production.
  • Single Supabase pooler connection string with modest pool settings; high concurrency would need tuning.
  • External dependencies. Groq + HuggingFace must be reachable and correctly scoped (e.g. the ticket-priority XGBoost model can't run on HF's serverless inference).
  • CORS allowlist is hard-coded to localhost dev origins — deployment needs the real frontend origin added.
  • Reload gotcha. Code changes need a real restart to take effect reliably.
  • Mixed concerns in places. Some routers/agents are large; ongoing refactor into services/ keeps them thin.
