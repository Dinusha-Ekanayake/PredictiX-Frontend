The LLM & Data-Injection Algorithm

Ground-to-high-level: what a Large Language Model actually is, what "data injection" means, the precise algorithm PredictiX uses to feed live database facts into the model, how it's implemented, the files involved, how to run it, and its limits.

1 · What is an LLM (ground level)?

A Large Language Model is a neural network trained to do one deceptively simple thing: predict the next token (a token ≈ a word-piece) given all the tokens before it. Stack that prediction billions of times over a huge corpus and the model learns grammar, facts, reasoning patterns and style.

  • Tokens — text is chopped into sub-word units. "maintenance" might be ["main","ten","ance"].
  • Autoregressive generation — to write a sentence, the model emits one token, appends it, and predicts the next, repeating until done.
  • Transformer + attention — each token "attends" to the others, so the model weighs context when choosing the next word.
  • Context window — the maximum tokens it can read at once (prompt + output). Everything the model "knows for this request" must fit here.
  • Temperature — randomness of the choice. Low (≈0.2) = focused/deterministic; high = creative/varied.

Key limitation to remember: an LLM does not know your data. It only knows general patterns from training. To make it talk about your 1,156 assets, you must put that data into the prompt — that's data injection.

2 · What is "data injection"?

Data injection is the act of placing your real, live information directly into the model's prompt (its context window) at request time, so the model generates text grounded in those facts. In PredictiX this is the engine of RAG (Retrieval-Augmented Generation): we retrieve/compute the right facts, then inject them into the prompt before generating.

PROMPT = [ SYSTEM INSTRUCTIONS ] ← how to behave + output JSON + [ LIVE DATABASE DATA ] ← injected facts (your warehouse) + [ KNOWLEDGE BASE CONTEXT ] ← injected standards (ISO/SMRP/OEM) │ ▼ LLM (Llama 3.3) │ ▼ JSON { insight_summary, risk_analysis, ... } ← grounded narrative

Two kinds of data are injected in this project:

Injected blockBuilt byContains

3 · Injection vs fine-tuning (why we inject)

Data injection (what we do)Fine-tuning
MechanismPut facts in the prompt at runtimeRetrain model weights on your data
FreshnessAlways current (reads the DB live)Frozen at training time
Cost/effortNone — just prompt assemblyExpensive, slow, needs ML ops
NumbersExact (from SQL), not memorisedModel may hallucinate memorised values
Best forFacts that change (your fleet)Style/behaviour, not facts
For a reporting tool whose numbers change every day, injection is the correct choice — the model stays a fluent writer, while the database stays the single source of truth.

4 · How it's used in this project

The LLM sits at step 4 of 5 in the report pipeline (run_warehouse_agent() in app/agents/report_agents.py):

  1. Build context — build_warehouse_context(db) runs all SQL into a dict.
  2. Retrieve KB — the TF-IDF vector store fetches relevant standards per section.
  3. Annotate — deterministic Python computes every number (no LLM).
  4. Generate (LLM) — inject data + KB into the prompt, call Groq Llama 3.3, get JSON prose.
  5. Guard — post-process: append authoritative trend facts, flag contradictions, strip stray tags.

The LLM produces only the readable prose in 5 keys. All charts, KPIs and tables come from the injected numbers — so even if the prose were imperfect, the figures stay exact.

5 · The data-injection algorithm (step by step)

5.1 Collect & deduplicate

Assets accumulate many prediction rows over time. The algorithm first reduces to one latest row per asset so health bands can't double-count:

SELECT DISTINCT ON (asset_id)
       asset_id, health_score, failure_probability, risk_level, days_until_maintenance
FROM asset_failure_predictions
ORDER BY asset_id, created_at DESC

5.2 Aggregate into metrics

Counts, averages and GROUP BY breakdowns become plain numbers/dicts: fleet by type & status, health buckets (≥80 / 60–79 / <60 / <50), risk distribution, cost forecast, maintenance events (windowed), tickets, MTTR, component health, vendors.

5.3 Pre-compute every derived figure in Python

Rates and ratios are computed here — never left to the model: e.g. critical_rate_pct, at_risk_rate_pct, pm_ratio_pct = preventive ÷ all events (≤100%). These become the authoritative values the prose must reuse verbatim.

5.4 Window anchoring (a real-world fix)

The 3-month maintenance window anchors to the latest activity, not "today", so seed/demo data dated in the past still populates the report; the 3-month total equals the sum of the monthly buckets (they can never disagree).

5.5 Serialize to a compact, labelled text block

_context_to_prompt_text(ctx) turns the dict into a token-efficient, human-readable block the model parses reliably:

▶ FLEET ASSETS (Total: 1156)
  Active: 800 | Under Maintenance: 15 | ...
▶ HEALTH & PREDICTIVE ANALYTICS
  Average Fleet Health Score: 68%
  Critical Rate: 29.5% (341 of 1156)   ← use this EXACT value
  Top SHAP Failure Drivers: engine hours, coolant temp, ...
▶ MAINTENANCE EVENTS (Last 3 Months)
  Total Events: 1250 | PM Ratio: 99.0% | ...

5.6 Assemble the final prompt & inject

combined_prompt = (
  f"LIVE DATABASE DATA:\n{context_text}\n\n"
  f"KNOWLEDGE BASE CONTEXT (ISO 55000 / SMRP):\n{kb_full_context}"
)
messages = [
  SystemMessage(content=WAREHOUSE_SYSTEM_PROMPT),
  HumanMessage(content=f"Generate the full KB-Enhanced warehouse report:\n\n{combined_prompt}"),
]
That's the whole "injection": the live numbers + standards now live inside the model's context window for this single request. No training, no database access by the model itself.

6 · The LLM-call algorithm (step by step)

  1. Instantiate the client: _get_llm(temperature=0.25) → ChatGroq(model_name="llama-3.3-70b-versatile") (raises a clear error if GROQ_API_KEY is missing).
  2. Invoke: response = llm.invoke(messages). Groq tokenises the prompt, runs autoregressive generation, and returns the full completion.
  3. Clean: strip any ```` ``` ```` code fences the model may wrap around the JSON.
  4. Parse: json.loads(content); on failure, a regex extracts the first { ... } block; on total failure, fall back to putting the raw text in insight_summary.
  5. Guard: _guard_narrative() appends data-grounded trend facts & flags contradictions; _strip_kb_referenced() removes stray meta-tags.
  6. Return: { ai_sections, context, kb_annotations } to the router → frontend.
It's a single, stateless call per report — no multi-turn chat, no tool-calling. Simplicity = predictability and speed, at the cost of not being able to "ask the model to fetch more".

7 · Prompt engineering (how reliability is enforced)

WAREHOUSE_SYSTEM_PROMPT is where behaviour is controlled. It declares the role, demands a strict JSON object with exactly 5 keys, gives per-section instructions, and lays down STRICT RULES:

  • Use only numbers from the provided data — never invent or estimate.
  • Do not compute any percentage/ratio/delta — narrate the provided values (e.g. use the given PM Ratio / Critical Rate verbatim).
  • A part-of-whole ratio can never exceed 100%.
  • "Critical" = the <50% health band only; don't blend it with the at-risk (<60%) count.
  • Describe the est-vs-actual cost gap neutrally — don't assert "underspend"/"savings".
  • No markdown, no bullet points, no text outside the JSON, no "KB Referenced" meta-tags.
The core principle: numbers come from Python; only language comes from the LLM. Combined with low temperature and post-generation guards, this is what keeps an inherently probabilistic model producing a trustworthy document.

9 · How to use it

Configure

# PredictiX_backend/PredictiX_backend/.env
GROQ_API_KEY=gsk_xxxxxxxxxxxxxxxxx        # free key from console.groq.com
pip install -r requirements.txt           # includes langchain-groq

Tune (optional)

  • Model / temperature: _get_llm() in report_agents.py (model_name, temperature).
  • Behaviour / sections / rules: edit WAREHOUSE_SYSTEM_PROMPT.
  • What data is injected: edit build_warehouse_context() + _context_to_prompt_text().

Run & generate

uvicorn app.main:app --reload         # backend (restart fully after edits!)
# then: admin → /admin/warehouse → "Generate Report"
After editing the prompt or injection code, fully restart Uvicorn — a stale process is the usual reason a change "doesn't show up".

11 · Limitations

  • Hallucination risk in prose. The model can still phrase things loosely; mitigated by computing numbers in Python, strict rules, low temperature and guards — not eliminated. Spot-check narrative claims.
  • Context-window budget. All injected data + KB must fit the window; a much larger fleet/KB would need summarisation or stricter top-k retrieval.
  • JSON fragility. The model must return valid JSON; a regex fallback exists, but malformed output degrades to raw text in one field.
  • Single stateless call. No tool-use or follow-up — the model can't request missing data; everything must be injected up front.
  • External dependency & cost. Needs GROQ_API_KEY and network; subject to rate limits and model deprecation (the model id may need updating over time).
  • Determinism is partial. Even at low temperature, wording varies run-to-run; only the injected numbers are guaranteed stable.
  • Prompt coupling. Section instructions and the injected text format are tightly coupled — changing one without the other can confuse the model.
