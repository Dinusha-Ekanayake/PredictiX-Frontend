The Warehouse Report

A ground-to-high-level guide: what this report is, how it works inside PredictiX, every file involved, how to run it, how it was built, what it's made of, and where its limits are.

1 · What is the Warehouse Report?

The Warehouse Report is PredictiX's executive-grade, AI-generated intelligence document for a fleet/warehouse. In one click an admin turns the live operational database into a multi-page report that reads like it was written by a senior maintenance analyst who has also read the relevant engineering standards (ISO 55000/55001, SMRP, OEM service schedules, the Sri Lanka Factories Ordinance, FMEA).

It answers, for a manager: How healthy is my fleet? What's about to fail and why? What will maintenance cost? Where are the tickets piling up? What should I do first? — and it grounds every recommendation in both live data and codified domain knowledge.

It blends three kinds of intelligence

LayerSourceExample output
Live factsSupabase Postgres (assets, predictions, tickets, events)"341 critical assets, 1,250 maintenance events in 3 months"
Domain knowledgeCurated Knowledge Base + ML explainability (SHAP)"Engine hours >500h → overdue (OEM interval)"
NarrativeLLM (Groq Llama 3.3) grounded by the two aboveThe readable executive prose in each section
Why "KB-Enhanced RAG"? RAG = Retrieval-Augmented Generation. The LLM is given ("augmented" with) the retrieved knowledge + live numbers before it writes — like an open-book exam. The "KB" is PredictiX's curated maintenance knowledge base.

2 · How it's used in this project

The report lives in the admin Warehouse section. The journey:

  1. An admin opens /admin/warehouse (the warehouse dashboard).
  2. They click “Generate Report” in the page header.
  3. A full-screen modal opens and immediately calls the backend to generate the report (~10–25s).
  4. The modal renders 7 sections with live KPIs, interactive charts, and AI narrative.
  5. In §3 the admin can tick specific critical assets and click “Summarise ticked assets” to attach per-asset AI summaries.
  6. They click “PDF” to export a print-ready, branded PDF (and the server is notified of the print).

3 · Architecture & data flow

Two applications cooperate: a Next.js frontend and a FastAPI backend, over a Supabase Postgres database, with a Groq-hosted LLM and several ML models.

┌─────────────── FRONTEND (Next.js / React / TS) ───────────────┐ │ admin/warehouse/page.tsx │ │ │ click "Generate Report" │ │ ▼ │ │ WarehouseReportModal.tsx ──GET /warehouse-dashboard/generate-report └───────────────────────────────────────────────────────────┬─┘ │ ┌──────────────── BACKEND (FastAPI / SQLAlchemy) ────────────▼─┐ │ routers/warehouse_dashboard.py → run_warehouse_agent(db) │ │ │ │ 1. build_warehouse_context(db) ── queries ALL tables ──► Supabase │ 2. KBVectorStore.retrieve() ── TF-IDF + cosine ──► KB_DOCUMENTS │ 3. kb_annotator.*() ── deterministic numbers │ │ 4. LLM (Groq Llama 3.3 70B) ── writes 5 prose sections │ │ 5. _guard_narrative + _strip_kb_referenced (post-process) │ │ │ │ returns { ai_sections, context, kb_annotations } │ └───────────────────────────────────────────────────────────┬─┘ │ JSON ┌─────────────────────────── FRONTEND ───────────────────────▼─┐ │ ReportStep renders sections + recharts │ │ (optional) tick assets → POST /asset-summaries/generate │ │ click PDF → professionalPdfExport.ts → print via iframe │ └───────────────────────────────────────────────────────────────┘

The 5-step backend pipeline (the heart)

  1. Data injection — build_warehouse_context() runs ~30 live SQL aggregations into one context dict.
  2. Retrieval — the KB vector store finds the most relevant standards for each section (semantic search).
  3. Annotation — deterministic Python computes all the numbers (rates, ratios, thresholds, recommendations) — never the LLM.
  4. Generation — the LLM writes 5 flowing prose sections, grounded by steps 1–3.
  5. Guarding — post-processing appends authoritative trend facts, flags contradictions, and strips unwanted tags.

6 · How it was implemented

Step 1 — Data injection (build_warehouse_context)

~30 SQLAlchemy aggregations build one dictionary of everything: fleet counts, health bands (deduplicated to the latest prediction per asset), risk distribution, SHAP features, cost forecasts, maintenance events (windowed to the 3 calendar months ending at the latest activity), tickets, MTTR, users, component health, vendors. Every number the report shows originates here or in the annotator.

Design rule: the window anchors to the latest data, not “today”, so seed/demo data dated in the past still populates the report. Totals are the sum of the monthly buckets, so they can never disagree.

Step 2 — Retrieval (the vector store)

The KB is embedded once with scikit-learn TfidfVectorizer (unigrams+bigrams, English stop-words, sublinear TF) into a small in-memory matrix. For each report section a query string is embedded the same way and compared by cosine similarity; the top-k chunks above a score floor are concatenated into the prompt.

q_vec  = vectorizer.transform([query])          # query → same space
scores = cosine_similarity(q_vec, matrix)[0]    # compare to all chunks
top_idx = argsort(scores)[::-1][:top_k]         # rank, keep best k
TF-IDF (not neural embeddings) was chosen deliberately: the KB is tiny (~15 docs), sklearn is already installed, there's no model download/GPU, and startup is instant. Supabase's pgvector is reserved for a future dense-embedding upgrade.

Step 3 — Deterministic annotation (kb_annotator)

Every computed figure — critical rate, PM ratio, benchmark deltas, SHAP thresholds, 3-tier recommendations — is produced in plain Python here, not by the LLM. This is the single most important reliability decision in the system.

Step 4 — Generation (the LLM)

The live context text + retrieved KB are injected into WAREHOUSE_SYSTEM_PROMPT and sent to Groq Llama 3.3 70B (low temperature). The model returns strict JSON with 5 keys (insight_summary, risk_analysis, maintenance_intelligence, pattern_and_trend, conclusion). The prompt forbids the model from computing percentages/ratios itself — it narrates the provided numbers.

Step 5 — Guarding & cleanup

  • _guard_narrative() appends authoritative trend facts and flags any LLM claim that contradicts the computed trend directions.
  • _strip_kb_referenced() deletes stray "KB Referenced" meta-tags from the prose.
  • Numeric guardrails in the annotator keep ratios ≤100% and definitions consistent across pages.

7 · The PDF engine

professionalPdfExport.ts doesn't use a heavy PDF library. It:

  1. Builds a complete, print-styled HTML string with generateProfessionalHTML() — page-by-page sections, hand-rolled SVG charts (donut/bar/line), and tables.
  2. Writes that HTML into a hidden iframe and calls the browser's native print() (downloadProfessionalPDF()), which the user saves as PDF.
  3. Before building, it optionally fetches per-asset AI summaries for the ticked critical assets.
  4. After printing it pings /warehouse-dashboard/notify-print.
Because the on-screen modal (recharts) and the PDF (SVG) are two separate renderers, both read the same backend payload — so the numbers always match even though the visuals differ.

9 · How to use it (setup → run → generate)

A. One-time setup

Backend

cd PredictiX_backend/PredictiX_backend
python -m venv .venv && .venv\Scripts\activate     # Windows
pip install -r requirements.txt                      # incl. xgboost, nltk, joblib

Create .env with at least:

DATABASE_URL=postgresql+psycopg2://...     # or PROJECT_REF + DATABASE_PASSWORD
GROQ_API_KEY=gsk_xxx                        # required for the LLM
HF_TOKEN=hf_xxx                             # for HF models (summaries/ticket AI)
HF_ASSET_SUMMARIZATION_REPO=...
HF_TICKET_PRIORITIZATION_REPO=...
HF_TICKET_CATEGORIZATION_REPO=...
# DISABLE_HF_MODELS=true   # optional: skip HF warmup in dev

Frontend

cd PredictiX-Frontend
npm install
# .env.local
NEXT_PUBLIC_API_URL=http://127.0.0.1:8000

B. Run

# terminal 1 — backend
cd PredictiX_backend/PredictiX_backend
uvicorn app.main:app --reload

# terminal 2 — frontend
cd PredictiX-Frontend
npm run dev

C. Generate the report

  1. Log in as an admin, go to /admin/warehouse.
  2. Click “Generate Report” → wait ~10–25s.
  3. Review the 7 sections; in §3 tick critical assets → “Summarise ticked assets” if you want AI summaries.
  4. Click “PDF” → in the print dialog choose “Save as PDF”.
Golden rule: after pulling/merging or editing backend code, fully restart Uvicorn before regenerating — auto-reload can miss changes that arrive via git, leaving the running process on stale code (the usual cause of “zeros / not available” sections).

11 · Limitations & known issues

  • LLM faithfulness. Free-text models can paraphrase/invent numbers. Mitigated by computing all figures in Python, hardening the prompt, and post-generation guards — but prose should still be spot-checked.
  • TF-IDF retrieval matches distinctive vocabulary, not deep semantics. Fine at ~15 docs; a larger KB should move to dense embeddings + pgvector.
  • Single warehouse. The context builder reads one warehouse (Warehouse.first()); multi-warehouse needs a filter/parameter.
  • Time-windowed data. Anchoring to latest activity keeps demo data visible but means “last 3 months” follows the data, not the wall clock.
  • External model availability. Ticket priority/category and asset summaries depend on HuggingFace (token scope, model serving). The HF Inference API can't serve raw XGBoost — needs local .pkl loading.
  • Data quality gaps. Null vehicle_type (“Other”) and null manufacture_year appear as explicit “Unknown” buckets; fixing them is a source-data task.
  • PDF via browser print. Output depends on the browser's print engine; no server-side PDF rendering.
  • “Critical” is a product definition (health < 50%), standardised across pages — distinct from the operational status='critical' column.
  • Operational gotcha: code changes need a real server restart to take effect.
